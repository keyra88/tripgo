# TripGo — Trip Service

## 1. Инструкция по запуску

### 1.1. Локальный запуск через `tripgoctl` и `make`

```bash
# 1. Запуск окружения с PostgreSQL
tripgoctl environment start

# 2. Применение миграций базы данных
make migrate

# 3. Запуск сервиса
make run
```

Сервис слушает HTTP-запросы на адресе `http://localhost:8080`.

### 1.2. Запуск в Docker

Сервис собирается с помощью многостадийного Dockerfile на базе `gcr.io/distroless/static-debian12:nonroot`:

```bash
# Сборка образа
docker build -f deploy/Dockerfile -t tripgo-service:local .

# Запуск контейнера в сети окружения
docker run -d --name tripgo-app \
  -p 8080:8080 \
  -e DATABASE_URL="postgres://tripgo:tripgo@host.docker.internal:21032/tripgo?sslmode=disable" \
  -e HTTP_ADDR=":8080" \
  -e SHUTDOWN_TIMEOUT="10s" \
  tripgo-service:local
```

## 3. Принятые решения

### 3.1. Уровень изоляции транзакций: `Read Committed`

* **Почему выбран**:
  1. `Read Committed` является стандартным уровнем изоляции в PostgreSQL и обеспечивает оптимальный баланс между высокой производительностью под конкурентной нагрузкой и отсутствием «грязных» чтений.
  2. Защита от бизнес-конфликтов (запрет двух активных поездок у водителя) гарантируется на уровне СУБД с помощью уникального частичного индекса `trips_driver_id_active_idx`. Уровня `Read Committed` достаточно, так как уникальные индексы в PostgreSQL атомарно проверяются при вставке вне зависимости от уровня изоляции.
  3. Для завершения поездки используется атомарный `UPDATE trips SET status = 'completed' WHERE id = $1 AND status = 'active'` с предикатом статуса. В `Read Committed` PostgreSQL при обновлении строки берет эксклюзивную блокировку строки (`FOR UPDATE`), что исключает возможность гонки при параллельных вызовах `finish`.
  4. Более строгие уровни (`Repeatable Read`, `Serializable`) требуют механизма перезапуска транзакций (*retry*) при ошибках сериализации (`40001 serialization_failure`), что избыточно для текущей модели данных.

### 3.2. Менеджер транзакций (`TxManager`)

* **Интерфейс**:
  ```go
  type TxManager interface {
      Do(ctx context.Context, fn func(ctx context.Context) error) error
  }
  ```
* **Реализация**:
  - Контекстный подход: открытая транзакция `pgx.Tx` сохраняется в `context.Context` по закрытому ключу `txKey`.
  - Репозиторий прозрачно извлекает исполнителя (`txmanager.ExtractTx(ctx)`): если транзакция присутствует в контексте, запросы выполняются внутри нее; если нет — напрямую через пул `pgxpool.Pool`. Репозиторий не принимает транзакцию отдельным аргументом.
  - **Надёжный `Rollback` и `Commit`**: откат выполняется с независимым контекстом `context.Background()` и таймаутом `DATABASE_QUERY_TIMEOUT`, гарантируя освобождение ресурсов в СУБД даже при отмене клиентского запроса. Коммит выполняется строго в контексте запроса (`context.WithTimeout(ctx, DATABASE_QUERY_TIMEOUT)`); если контекст запроса уже отменён, транзакция не коммитится, а откатывается.
  - **Поддержка вложенности**: при повторном вызове `Do` внутри уже существующей транзакции менеджер переиспользует текущую транзакцию, не открывая вторую.
  - Одиночные запросы вне транзакции (`GET /api/v1/trips/{tripId}` и `/ready`) также явно ограничены таймаутом `DATABASE_QUERY_TIMEOUT`.

### 3.3. Graceful Shutdown с жёстким лимитом общего бюджета

* Сервис слушает сигналы `SIGINT` и `SIGTERM`.
* Процедура завершения запускается в фоновой горутине:
  1. `srv.Shutdown(shutdownCtx)` прекращает приём новых подключений и ожидает завершения текущих запросов.
  2. `pool.Close()` закрывает все соединения с базой данных.
* Главный поток через `select` контролирует общий бюджет времени `SHUTDOWN_TIMEOUT`. Если СУБД или запросы зависли дольше заданного таймаута, вызывается `os.Exit(1)`, гарантируя, что процесс завершится принудительно ровно по истечении бюджета.

### 3.4. Строгая валидация входящих тел запросов

* Для ручки создания поездки `POST /api/v1/trips` реализована строгая схема валидации JSON:
  - **Защита от мусора и лишних токенов**: проверяется отсутствие хвостовых данных (`{...} {}`).
  - **Регистрозависимость и `additionalProperties: false`**: допускаются строго поля `"user_id"`, `"driver_id"`, `"start_point"`, `"end_point"`, `"price"`. Поля с некорректным регистром (например, `"PrIcE"`) или неизвестные ключи отклоняются с ошибкой `400 invalid_request`.
  - **Проверка обязательности и запрет `null`**: пропуск любого из полей или передача `null` возвращает `400 invalid_request`. Допустимый ноль (`price: 0`) корректно принимается как валидная неотрицательная цена.
  - **Валидация координат**: поля `latitude` и `longitude` проверяются на диапазоны WGS 84 (`[-90, 90]` и `[-180, 180]`).

### 3.5. Перехват паник по стандарту RFC 9457 Problem Details

* Сервис использует кастомный middleware `middleware.Recoverer`, который перехватывает необработанные паники, логирует стектрейс и возвращает клиенту ответ `500 Internal Server Error` с заголовком `Content-Type: application/problem+json` и кодом `"internal_error"` в строгом соответствии с контрактом OpenAPI.

### 3.6. Запрет двух активных поездок на одного водителя

* На уровне схемы данных создан частичный уникальный индекс:
  ```sql
  CREATE UNIQUE INDEX trips_driver_id_active_idx ON trips (driver_id) WHERE status = 'active';
  ```
* При попытке одновременного или повторного создания поездки для водителя с уже активной поездкой PostgreSQL возвращает ошибку `23505` (`unique_violation`).
* Репозиторий перехватывает код ошибки `23505` и трансформирует ее в доменную ошибку `domain.ErrDriverBusy`, которая преобразуется хендлером в ответ `409 Conflict` со структурой RFC 9457 (`code: driver_busy`).

### 3.7. Идемпотентность `POST /api/v1/trips` по `Idempotency-Key` (задание со звёздочкой)

* **Хранение**: таблица `idempotency_keys` с временем жизни `expires_at = now() + 24h`.
* **Хеширование запроса с полной точностью**: вычисляется SHA-256 хеш канонического представления входных параметров. Для координат используется `strconv.FormatFloat(val, 'g', -1, 64)`, что исключает округление и обеспечивает сохранение микроразличий в координатах (разница даже в 7-м знаке возвращает `409 idempotency_conflict`).
* **Повторное использование истекшего ключа (TTL 24h)**: метод сохранения использует `INSERT ... ON CONFLICT (key) DO UPDATE`, поэтому при повторном использовании ключа спустя 24 часа запись атомарно перезаписывается для новой поездки без ошибки уникальности первичного ключа (`500`).
* **Защита от состояния гонки при одинаковом ключе**: транзакционный рекомендательный замок PostgreSQL `pg_advisory_xact_lock(hashtext(key))` сериализует конкурентные запросы с одним ключом.

### 3.8. Многостадийный Dockerfile (задание со звёздочкой)

* Многостадийная сборка:
  - Слой сборщика: `golang:alpine`, компиляция статического бинарника без зависимостей (`CGO_ENABLED=0`, `-trimpath`, `-ldflags="-s -w"`).
  - Финальный образ: `gcr.io/distroless/static-debian12:nonroot`.
* Безопасность: процесс запускается от непривилегированного пользователя `nonroot:nonroot` (UID 65532).
* Чистота образа: `.dockerignore` исключает `.git`, тесты, документацию и локальные `.env` файлы.
* Размер итогового образа: **21.7 MB**.

## 4. Команды Makefile

* `make generate` — кодогенерация роутера OpenAPI (`oapi-codegen`) и моков (`mockgen` через `go:generate`).

* `make lint` — запуск полного набора линтеров (`golangci-lint`) со строгой проверкой архитектурных слоёв через `depguard`.

## 5. Архитектура сервиса

Сервис построен по принципам чистой архитектуры (Clean Architecture / Ports & Adapters). Кодовая база разделена на независимые слои с направлением зависимостей строго **снаружи внутрь**.

```
                              ┌────────────────────────┐
                              │    cmd/trip-service    │  (Composition Root / main)
                              └───────────┬────────────┘
                                          │
                   ┌──────────────────────┴──────────────────────┐
                   ▼                                             ▼
       ┌────────────────────────┐                   ┌────────────────────────┐
       │     internal/http      │                   │  internal/repository   │
       │  (Транспортный слой)   │                   │  (Инфраструктура БД)   │
       └───────────┬────────────┘                   └────────────┬───────────┘
                   │                                             │
                   │  зависит от интерфейсов usecase             │  реализует интерфейсы
                   ▼                                             │  репозиториев
       ┌────────────────────────┐                                │
       │    internal/usecase    │◄───────────────────────────────┘
       │ (Бизнес-сценарии /     │
       │   порты-контракты)     │
       └───────────┬────────────┘
                   │
                   │  чистая бизнес-логика
                   ▼
       ┌────────────────────────┐
       │    internal/domain     │  (Сущности, методы перехода состояний,
       │   (Ядро приложения)    │   доменные ошибки и валидация)
       └────────────────────────┘
```

### 5.1. Назначение слоёв

| Слой | Путь пакета | Назначение и ответственность |
|---|---|---|
| **Domain** | `internal/domain/trip` | Ядро бизнес-логики: сущность `Trip`, правила переходов состояний (`Trip.Finish(at time.Time)`), валидация полей модели (`Trip.Validate()`), доменные ошибки (`ErrTripNotFound`, `ErrTripCompleted`, `ErrDriverBusy`, `ErrInvalidRequest`, `ErrIdempotencyConflict`) и тип ошибки валидации `ValidationError`. Не зависит ни от каких библиотек, фреймворков и инфраструктуры. |
| **Model** | `internal/model` | Межуровневые типы и структуры данных (`Trip`, `Point`, `Status`, `IdempotencyRecord`), позволяющие слоям обмениваться сущностями без циклических импортов. |
| **Usecase** | `internal/usecase/trip/{create,get,finish}` | Сценарии использования приложения. Координируют выполнение бизнес-логики: вызывают методы домена, управляют транзакциями через `TxManager`, сохраняют/читают данные через интерфейсы репозиториев, регистрируют бизнес-метрики. |
| **Transport** | `internal/http/trip/{create,get,finish}` | HTTP-адаптеры: строгая десериализация и валидация JSON-запросов, вызов соответствующего usecase, сериализация ответа. `internal/http/trip/handler.go` объединяет адаптеры в реализацию интерфейса `api.ServerInterface`. |
| **Error Mapping** | `internal/http/domainerror` | Единая точка трансляции доменных ошибок в структуру RFC 9457 `application/problem+json`. Скрывает внутренние детали инфраструктуры (при 500 никогда не возвращает SQL-ошибки или стектрейсы клиенту). |
| **Middleware** | `internal/http/middleware` | Фиксированная цепочка промежуточной обработки: `Recover -> Tracing -> Logging -> Metrics -> router`. |
| **Repository** | `internal/repository/trip` | Адаптер к базе данных PostgreSQL. Реализует интерфейсы, требуемые usecase, с использованием SQL-билдера `squirrel` и пула `pgxpool.Pool`. |
| **Infrastructure** | `internal/infra/{postgres,telemetry}` | Инфраструктурные компоненты: подключение к PostgreSQL с `otelpgx`, контекстный менеджер транзакций `txmanager.TxManager`, OpenTelemetry SDK (TracerProvider, MeterProvider, OTLP HTTP-экспортеры, контекстный handler для `log/slog`). |
| **Container** | `internal/container` | Composition Root: явное связывание всех зависимостей сервиса в коде без глобальных переменных, скрытых синглтонов или сторонних DI-библиотек. |
| **App Entrypoint**| `cmd/trip-service` | Точка входа в приложение: загрузка конфигурации, сборка контейнера, запуск HTTP-сервера и координация Graceful Shutdown по тайм-бюджету. |

### 5.2. Правила зависимостей и контроль через `depguard`

Зависимости направлены исключительно внутрь. Направление импортов контролируется линтером `depguard` в `.golangci.yml`:
1. `internal/domain`: **запрещено** импортировать `net/http`, `chi`, `pgx`, `squirrel`, `otel`, `api`.
2. `internal/usecase`: **запрещено** импортировать `net/http`, `chi`, `pgx`, `squirrel`, `api`.
3. `internal/http/*`: **запрещено** импортировать `internal/repository/*` и `internal/infra/*`.

### 5.3. Расположение интерфейсов

Интерфейсы объявляются на стороне **потребителя** (внутри пакета, которому требуется зависимость), а не на стороне реализации:
- `internal/usecase/trip/create/contract.go`: интерфейсы `TripRepository` и `TxManager`.
- `internal/usecase/trip/finish/contract.go`: интерфейсы `TripRepository` и `TxManager`.
- `internal/usecase/trip/get/contract.go`: интерфейс `TripRepository`.
- `internal/http/trip/{create,get,finish}/contract.go`: интерфейсы соответствующих сценариев использования.
- `internal/http/trip/handler.go`: узкий интерфейс `Pinger` (`Ping(ctx context.Context) error`).

**Почему интерфейсы объявлены у потребителя:**
1. **Принцип инверсии зависимостей (DIP)**: высокоуровневые модули (usecase) не должны зависеть от низкоуровневых модулей (репозиторий PostgreSQL). Оба должны зависеть от абстракций.
2. **Минимализм и изоляция (ISP)**: каждый юзкейс определяет ровно те методы, которые необходимы для его выполнения. Например, для сценария `get` требуется только `GetTripByID`, поэтому мок в тестах тривиален и не требует реализации методов создания или блокировок.
3. **Расширяемость**: при добавлении в будущем альтернативного транспорта (например, gRPC или очередей сообщений Kafka) сценарии использования и домен останутся неизменными — новый транспортный адаптер просто обратится к существующим usecase.
